# examples/

Two minimal but complete workflows — `refinement` and `inner-loop` — wired
together as a testing ground for every part of the framework: parsers,
validator, planner, multi-workflow registry routing, catalog dispatch, and
trust-grant relaxation. None of the commands below need to touch a real
issue tracker.

For the rules behind the workflow JSON in this example, see
[`../docs/workflow-authoring.md`](../docs/workflow-authoring.md). For the
underlying design principles, see [`../docs/state-machine-principles.md`](../docs/state-machine-principles.md).

## Layout

```
examples/
  .workflow/                                      # PM agent home
    config.json                                   #   agent identity (role=pm)
    workflows/                                    #   shared workflow registry
      refinement-states.json                   #     CANONICAL — 4 states, 2 [hitl] gates
      refinement-states.mermaid                #     generated visualization
      refinement-hcps.json                        #     2 HCPs (1 block, 1 audit)
      inner-loop-states.json                   #     CANONICAL — 8 states, 2 [hitl] gates
      inner-loop-states.mermaid                #     generated visualization
      inner-loop-hcps.json                        #     2 HCPs (1 block, 1 audit)
      roles.json                                  #     pm + developer
      ready-packet-template.md                    #     agent_prepares pointers
      wont-fix-note-template.md
      merge-packet-template.md
      bounce-back-note-template.md
    trust-grants/                                 #   shared grants
      refinement/
        ready_for_dev.json                        #     relaxes block → audit

  dev-home/                                       # Developer agent home
    .workflow/
      config.json                                 #   role=developer; points at
                                                  #   ../.workflow/{workflows,trust-grants}
```

`<name>-states.json` is the source of truth. The matching `.mermaid`
file alongside it is generated by `workflow generate-docs` — it's checked
in so GitHub renders the diagram, but authors edit JSON only.

**Two agent homes** sharing one workflow registry: this is the canonical
production setup. Each agent has its own identity but reads the same
artifacts. The dev-home's `config.json` uses relative `workflow-dir` and
`grants-dir` keys (anchored to the agent home) to point at the PM home's
directories — a real team would put the workflows in a shared location and
each agent's home would point at it the same way.

Drive the tool with `--agent-home examples` (PM) or `--agent-home
examples/dev-home` (Developer). The role on `config.json` becomes the
planner's actor identity for `claim`, `advance`, and the HITL gates'
triggering-role checks.

## Refinement workflow

```
[*] ──issue created──▶ raw
                        │
                        │ PM claims raw
                        ▼
                     refining ──────────────────────┐
                        │                           │
                        │ PM marks ready [hitl]     │ PM marks wont-fix [hitl]
                        ▼                           ▼
                  ready_for_dev               wont_fix
                        │                           │
                        │ to process inner-loop     │ terminal (abandoned)
                        ▼                           ▼
                       [*]                         [*]
```

| Gate          | Default level | Reversibility    | Why                                                        |
|---------------|---------------|------------------|------------------------------------------------------------|
| `ready_for_dev` | block       | reversible-slow  | PM judgement on scope; work has started, slow to unwind.   |
| `wont_fix`    | audit         | reversible-fast  | Low-stakes triage call; reopening an issue is cheap.       |

## Inner-loop workflow

```
[*] ──from process refinement──▶ ready_for_dev
                                   │
                                   │ developer claims ready_for_dev
                                   ▼
                            implementing ◀──┐
                              │   │         │
                              │   │ bounce  │ revisions
                  opens PR    │   │ [hitl]  │ requested
                              ▼   ▼         │
                            staged ─────────┘
                              │   │
                              │   │ developer cancels PR
                  merge to    │   ▼
                  main [hitl] │  abandoned_dev ──▶ [*] (abandoned)
                              ▼
                            merged ──▶ [*] (shipped)

                            bounced_back ──▶ [*] (iterated)
```

### The handoff: `ready_for_dev` is shared

`ready_for_dev` appears in **both** workflows — it's the shared resting state
that connects the two processes:

- In refinement: `refining → ready_for_dev → [*]: to process inner-loop`. The
  state is terminal-iterated from refinement's view; the PM hands it off here.
- In inner-loop: `[*]: from process refinement → ready_for_dev → implementing`.
  The state is resting (claim-role=developer); the developer picks it up here.

An issue with `state:ready_for_dev` is materially the same issue between the
two workflows — there's no re-labelling. The registry routes operations on it
to inner-loop (which loads first alphabetically and wins the
state-name-uniqueness index for the shared state). The PM's `advance --to
ready_for_dev` still works because it operates on an issue currently at
`state:refining`, which routes to refinement and finds the
`refining → ready_for_dev` transition there.

Convention: when sharing handoff states, name workflows so the **receiver**
sorts alphabetically before the **sender** (`inner-loop` < `refinement`), so
the registry's first-wins index points new operations at the right workflow.

| Gate          | Default level | Reversibility   | Why                                                                  |
|---------------|---------------|-----------------|----------------------------------------------------------------------|
| `merge_to_main` | block       | reversible-slow | Code review; revert PR exists but is disruptive.                     |
| `bounce_back` | audit         | reversible-fast | Dev calls the packet wrong; PM can re-refine immediately. Audit catches patterns. |

## The trust grant

`trust-grants/refinement/ready_for_dev.json` relaxes `ready_for_dev` from
**block** to **audit** for the example team. The grant is keyed by
gate name and applies wherever that gate appears in any workflow — the
inner-loop's gates (`merge_to_main`, `bounce_back`) aren't named in any
grant, so they fall back to catalog defaults.

## Try it out

All commands use `--dry-run` so nothing touches GitHub.

**Validate both workflows** (cross-checks workflow ↔ catalog ↔ grants):

```bash
uv run workflow --agent-home examples validate
```

**Inspect the registry**:

```bash
uv run workflow --agent-home examples doctor
# → 2 workflows discovered: inner-loop, refinement
```

**Regenerate the mermaid visualizations** (after editing JSON):

```bash
uv run workflow --agent-home examples generate-docs
# → Rendered examples/.workflow/workflows/inner-loop-states.mermaid
# → Rendered examples/.workflow/workflows/refinement-states.mermaid
```

### Refinement (PM agent home)

**Audit-gated `wont_fix`** (catalog default):

```bash
uv run workflow --agent-home examples --dry-run \
  advance --to wont_fix --issue 1 \
  --packet-from examples/.workflow/workflows/wont-fix-note-template.md
# → set_state=wont_fix, set_audit_pending=wont_fix (record-action)
```

### Inner-loop (developer agent home)

**Block-gated `merge_to_main`** (catalog default — code review):

```bash
uv run workflow --agent-home examples/dev-home --dry-run \
  advance --to merged --issue 1 \
  --packet-from examples/.workflow/workflows/merge-packet-template.md
# → set_awaiting_gate=merge_to_main (await-signal)
```

**Audit-gated `bounce_back`** (catalog default — dev judgment):

```bash
uv run workflow --agent-home examples/dev-home --dry-run \
  advance --to bounced_back --issue 1 \
  --packet-from examples/.workflow/workflows/bounce-back-note-template.md
# → set_state=bounced_back, set_audit_pending=bounce_back (record-action)
```

### Dry-run caveat for the shared handoff state

`ready_for_dev` lives in both workflows. With a real issue, the controller
reads the issue's current state from the backend and routes correctly: an
issue at `state:refining` routes to refinement, an issue at
`state:ready_for_dev` routes to inner-loop. In **dry-run** mode the backend
read fails, so the controller falls back to routing by the `--to` destination
— and `ready_for_dev` resolves to inner-loop (alphabetical first-wins). That
means the PM-side `advance --to ready_for_dev` demo only works against a real
issue currently at `state:refining`. To exercise refinement's `ready_for_dev`
gate end-to-end you need a real issue (or a future tool flag that lets you
inject a pre-state in dry-run).

## Editing the example

Every file is small and deliberately minimal. Reasonable extensions:

- Add a **verdict-style HCP** with multiple destinations (e.g., a triage gate
  that goes to `ready_for_dev` OR `wont_fix`).
- Add a **trust grant for `merge_to_main`** in
  `.workflow/trust-grants/inner-loop/merge_to_main.json` to see a code-review
  gate relaxed to audit-level.
- Add an **expired trust grant** (set `expires_at` in the past) to see the
  validator's expiry warning.
- Add a **grant that violates `allowed_levels`** (e.g., declares `audit` on a
  catalog where it isn't allowed) to see the cross-artifact error.
- Add a **third workflow** (e.g., `hotfix`) to push the registry harder. Any
  state shared with refinement/inner-loop becomes a handoff state — name the
  workflow so the receiver of that state sorts alphabetically first.
